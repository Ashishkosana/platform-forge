# Project 1 — V1 design: durable step runner

**Gate:** V1 design. No implementation until this file is approved.

**Stack (locked):** Python 3.12 + PostgreSQL 16. Not Go. Not Redis. Not Celery/RQ/Temporal.

**Guarantee:** at-least-once step execution. Effectively-once **only** when the handler cooperates with the idempotency key we pass it. We will measure duplicate effects; we will not claim exactly-once.

This document is the thing you should be able to whiteboard. If a later implementation disagrees with a state transition here, the code is wrong.

---

## 1. What V1 is

A **linear pipeline of named steps**, persisted in Postgres, executed by **N worker OS processes** that claim work with a **lease + fencing token**.

A job is not a blob the worker retries from the top. Each step has its own status, attempt log, and lease. Step 2 does not run until step 1 has a `succeeded` row.

Distribution in V1 means: several worker processes, one database, lease steal on expiry. It does not mean a broker, a scheduler replica set, or a custom consensus protocol.

### In

- `POST /jobs` with workflow name, JSON input, idempotency key
- Registered workflows: ordered `Step` list, in-process Python callables
- Claim / heartbeat / complete / fail against Postgres (`FOR UPDATE SKIP LOCKED`)
- Retry with exponential backoff **and jitter**, then dead-letter
- Cancel, stuck-job listing, explicit replay of a dead-lettered step
- Crash / overlap / poison / duplicate-submit drills with assertions
- `/metrics` + structured JSON logs

### Out

- DAGs, child workflows, signals, human-in-the-loop
- Workflow-as-code replay (Temporal model)
- `LISTEN/NOTIFY` (poll first; revisit if schedule-latency bench says so)
- Exactly-once for arbitrary HTTP
- Kafka, Redis, Kubernetes, a plugin ABI, a pretty dashboard

### Success

After `kill -9` of a worker, you can dump the three tables and they match the state machines in §3. Duplicate **attempts** are expected. Duplicate **effects** are a handler bug or a known naive-handler measurement.

## 2. Why Python + Postgres (and what that forces)

The plan’s default was Go. That is overridden.

| Choice | Decision | Defense |
| --- | --- | --- |
| Language | CPython 3.12 | Same language as Project 2; drills and HTTP stubs stay trivial. We pay with the GIL and with cooperative timeouts. |
| Concurrency | **OS processes** as the unit of crash; **threads as slots inside a process** | `kill -9` is a process signal. Threads share a fate. Default `--concurrency 1` for correctness drills; raise it for I/O benches. Do not use a multiprocessing pool that daemonizes away leases. |
| Async | **Sync workers** (psycopg in threads). Async optional only on the HTTP API process. | `asyncio` cancellation is not `kill -9`. Lease/heartbeat reasoning stays closer to the SQL. |
| DB driver | psycopg 3, server-side `now()` | Leases are computed in SQL. Worker wall clocks are not trusted (§6.4). |
| HTTP API | FastAPI + uvicorn, **separate process** from workers | API submits and inspects. It does not run handlers. Same registry module imported by both. |
| Migrations | One `schema.sql` applied at boot (idempotent) | Alembic is later, if we actually evolve the schema. |
| Queue | `SELECT … FOR UPDATE SKIP LOCKED` | One system of record. Inspect with `psql`. |

Python-specific honesty:

- Handler **timeout is cooperative**. We join the handler thread with a deadline; if it will not return, we **stop heartbeating** and let the lease expire (drill 2). We cannot preempt a stuck C extension.
- One in-process step per slot, not a green-thread scheduler pretending to isolate crashes.
- GIL: CPU-bound handlers scale with **processes**, not `--concurrency`.

## 3. State machines

### 3.1 Job

```text
                submit
                  |
                  v
              queued  ----------------+
                  |                   |
          first step claimed          |
                  v                   |
               running ---------------+-- cancel --> cancelled
                  |                   |
      last step succeeded             |
                  v                   |
              succeeded               |
                                      |
         any step dead_lettered ------> dead_lettered
                                      |
         replay of that step --------> running
```

| State | Meaning |
| --- | --- |
| `queued` | Inserted; step 1 is `pending`; no claim yet |
| `running` | At least one claim has happened; not terminal |
| `succeeded` | Every step `succeeded` |
| `dead_lettered` | A step exhausted retries; later steps stay `blocked` |
| `cancelled` | Terminal; workers must not start new attempts |

Transitions are SQL updates with **allowed-from** predicates. No in-memory job object is the source of truth.

Cancel is accepted from `queued` or `running` only. Replay is accepted from `dead_lettered` only, and only for the dead-lettered step (prior `succeeded` steps stay succeeded).

### 3.2 Step

```text
  insert job
      |
      |  seq == 1                    seq > 1
      v                              v
  pending                         blocked
      |                              |
      | claim                        | predecessor succeeded
      v                              v
  running <------ claim ------   pending
      |                              ^
      | success                      | fail, attempts remaining
      v                              | (run_after = now()+backoff)
  succeeded                          |
      |                         pending (run_after in the future
      |                          is not claimable yet)
      | fail, attempts exhausted
      v
  dead_lettered ---- explicit replay ----> pending
      |
  cancel of job -----> cancelled
```

| State | Claimable? |
| --- | --- |
| `blocked` | No |
| `pending` | Yes iff `run_after <= now()` (NULL means `now()`) |
| `running` | Yes iff `leased_until < now()` (steal) |
| `succeeded` / `dead_lettered` / `cancelled` | No |

`retry_wait` is **not** a separate status. It is `pending` with a future `run_after`. One less state to get wrong.

Unblocking: in the same transaction that marks step `k` succeeded, set step `k+1` from `blocked` → `pending` (`run_after = now()`). If `k` is last, mark the job `succeeded`.

## 4. Schema sketch

All timestamps `timestamptz`. All “now” comparisons use `now()` inside Postgres.

```sql
CREATE TABLE jobs (
  id                uuid PRIMARY KEY,
  workflow_name     text NOT NULL,
  idempotency_key   text NOT NULL,
  status            text NOT NULL,
  input             jsonb NOT NULL,
  created_at        timestamptz NOT NULL DEFAULT now(),
  updated_at        timestamptz NOT NULL DEFAULT now(),
  UNIQUE (workflow_name, idempotency_key)
);

CREATE TABLE steps (
  id              uuid PRIMARY KEY,
  job_id          uuid NOT NULL REFERENCES jobs (id),
  seq             int  NOT NULL,
  name            text NOT NULL,
  status          text NOT NULL,
  run_after       timestamptz NOT NULL DEFAULT now(),
  leased_until    timestamptz,
  worker_id       text,
  fencing_token   bigint NOT NULL DEFAULT 0,
  attempt_count   int NOT NULL DEFAULT 0,
  max_attempts    int NOT NULL,
  timeout_seconds int NOT NULL,
  output          jsonb,
  last_error      text,
  UNIQUE (job_id, seq),
  UNIQUE (job_id, name)
);

CREATE TABLE attempts (
  id             bigserial PRIMARY KEY,
  step_id        uuid NOT NULL REFERENCES steps (id),
  fencing_token  bigint NOT NULL,
  worker_id      text NOT NULL,
  started_at     timestamptz NOT NULL DEFAULT now(),
  finished_at    timestamptz,
  outcome        text NOT NULL,  -- started | succeeded | failed | rejected_fence | cancelled | timeout
  error          text,
  UNIQUE (step_id, fencing_token)
);

-- Laboratory side-effect ledger (drill handlers only, not a product store)
CREATE TABLE lab_effects (
  effect_key     text PRIMARY KEY,
  write_count    int NOT NULL,
  first_token    bigint NOT NULL,
  last_token     bigint NOT NULL,
  last_worker_id text NOT NULL,
  updated_at     timestamptz NOT NULL DEFAULT now()
);
```

Indexes (claim path first):

```sql
CREATE INDEX steps_claimable
  ON steps (run_after, id)
  WHERE status IN ('pending', 'running');

CREATE INDEX steps_job ON steps (job_id);

CREATE INDEX jobs_status ON jobs (status, created_at);
```

The claim index is **not** a perfect queue. `SKIP LOCKED` does not give fairness. Document that in interviews; do not add `PRIORITY` in V1.

Payloads live on `jobs.input` / `steps.output`. The claim CTE selects **ids only**, then a second query loads JSON. If the 100KB bench poisons the claim path anyway, that number is what justifies moving payloads — not aesthetics.

## 5. Protocols (the actual design)

### 5.1 Submit (idempotent)

Single transaction:

1. `INSERT INTO jobs … ON CONFLICT (workflow_name, idempotency_key) DO NOTHING RETURNING id`
2. If no row: `SELECT` the existing job and return it. **Do not** insert steps again.
3. If inserted: insert `N` steps. Seq 1 = `pending`, seq `>1` = `blocked`. Copy `max_attempts` / `timeout_seconds` from the registered workflow.

Concurrent duplicate submits: unique constraint is the lock. Exactly one job row.

API returns `201` + job on insert, `200` + same job on replay. Same body shape.

### 5.2 Claim

Worker loop (each slot):

1. Poll. Sleep `POLL_INTERVAL_SECONDS` (default 0.25s) if the claim returns nothing. **No LISTEN in V1.**
2. Run the claim SQL. Use DB time.

```sql
WITH picked AS (
  SELECT s.id
  FROM steps s
  JOIN jobs j ON j.id = s.job_id
  WHERE j.status IN ('queued', 'running')
    AND (
      (s.status = 'pending' AND s.run_after <= now())
      OR
      (s.status = 'running' AND s.leased_until < now())
    )
  ORDER BY s.run_after, s.id
  FOR UPDATE OF s SKIP LOCKED
  LIMIT 1
)
UPDATE steps s
SET status          = 'running',
    worker_id       = %(worker_id)s,
    fencing_token   = s.fencing_token + 1,
    leased_until    = now() + %(lease_ttl)s::interval,
    attempt_count   = s.attempt_count + 1,
    updated_at      = now()
FROM picked
WHERE s.id = picked.id
RETURNING s.*,
          (SELECT status FROM jobs WHERE id = s.job_id) AS job_status;
```

3. If this was a steal (`attempt_count` already ≥ 1 and previous status was `running`), increment metric `workflow_lease_expired_total`.
4. `INSERT INTO attempts (step_id, fencing_token, worker_id, outcome) VALUES (…, 'started')`.
5. If the job was `queued`, `UPDATE jobs SET status = 'running' WHERE id = ? AND status = 'queued'`.
6. Load job input + predecessor outputs. Invoke handler.

`FOR UPDATE OF s` avoids locking the job row during the queue scan so cancel/submit are not blocked by a long claim scan. Cancel still locks the job row on its own update.

Lease TTL default **15s**. Heartbeat every **5s**. Rule: `TTL >= 3 * heartbeat` so one missed beat does not steal.

### 5.3 Heartbeat

```sql
UPDATE steps
SET leased_until = now() + %(lease_ttl)s::interval,
    updated_at   = now()
WHERE id = %(step_id)s
  AND worker_id = %(worker_id)s
  AND fencing_token = %(token)s
  AND status = 'running'
RETURNING id;
```

Zero rows: **lost the lease.** Stop the handler path (set a slot-local `should_stop` flag). Do not write `succeeded`. Increment `workflow_fencing_reject_total` when a later complete also returns zero.

Heartbeat also `SELECT status FROM jobs WHERE id = ?`. If `cancelled`, treat as stop; complete path records `cancelled`, not success.

A dedicated heartbeat thread per in-flight slot. It uses its own DB connection. Do not share a psycopg connection across threads.

### 5.4 Complete — fencing is the write predicate

Success:

```sql
UPDATE steps
SET status        = 'succeeded',
    output        = %(output)s,
    leased_until  = NULL,
    worker_id     = NULL,
    updated_at    = now()
WHERE id = %(step_id)s
  AND fencing_token = %(token)s
  AND status = 'running'
RETURNING id;
```

Zero rows: another worker stole, or cancel won. Insert attempt outcome `rejected_fence`. **Do not** unblock the next step.

Non-zero: in the **same transaction**:

- Unblock `seq + 1` if it exists and is `blocked`.
- If no next step: `UPDATE jobs SET status = 'succeeded' WHERE id = ? AND status = 'running'`.
- `UPDATE attempts SET finished_at = now(), outcome = 'succeeded' WHERE step_id = ? AND fencing_token = ?`.

Failure (handler exception, timeout, `should_stop` from cancel):

- If job is `cancelled`: step → `cancelled`, attempt `cancelled`, no retry.
- Else if `attempt_count < max_attempts`:

```sql
UPDATE steps
SET status       = 'pending',
    run_after    = now() + %(backoff)s::interval,
    leased_until = NULL,
    worker_id    = NULL,
    last_error   = %(error)s,
    updated_at   = now()
WHERE id = %(step_id)s
  AND fencing_token = %(token)s
  AND status = 'running';
```

- Else: step → `dead_lettered`, job → `dead_lettered` (only from `running`).

Backoff (full jitter, **required in V1** — a herd drill without jitter fails the design):

```text
cap = min(max_backoff, base * 2^(attempt_count - 1))
delay = random.uniform(0, cap)
```

Defaults: `base = 0.5s`, `max_backoff = 30s`. Per-step overrides allowed on the workflow definition.

### 5.5 Why this is not a boolean lock

`status = 'running'` without `leased_until` is a lock that leaks when the process dies.

A lease is a **time-bounded lock whose expiry is defined by the database clock**. Steal is allowed. Therefore two handlers **can** overlap. The fencing token is a **monotonic epoch**; only the latest epoch may commit. That is effectively-once **state transition**, not exactly-once **side effect**.

Whiteboard sentence: *“We fence the row. We cannot fence the HTTP call that already left the process.”*

### 5.6 Clock skew

Workers never set `leased_until = datetime.now(UTC) + ttl`.

They pass an interval. SQL uses `now()`. A worker with a wrong wall clock can still *think* it should heartbeat, but it cannot extend a lease it does not own, and it cannot make an expired lease look valid in the claim query.

Drill 8 asserts claim/heartbeat SQL contains `now()` and that a monkeypatched Python clock does not change `leased_until`.

## 6. Worker and API processes

```text
[client] --HTTP-- [api process, FastAPI]
                       |
                       | INSERT jobs/steps
                       v
                   PostgreSQL
                       ^
                       | SKIP LOCKED claim / heartbeat / complete
                       |
              [worker process × N]
                 slot threads (default 1)
                 each slot: claim → heartbeat thread → handler → complete
```

`worker_id = f"{hostname}:{pid}:{slot}:{boot_uuid}"`.

Config (env):

| Variable | Default |
| --- | --- |
| `DATABASE_URL` | required |
| `LEASE_TTL_SECONDS` | `15` |
| `HEARTBEAT_INTERVAL_SECONDS` | `5` |
| `POLL_INTERVAL_SECONDS` | `0.25` |
| `WORKER_CONCURRENCY` | `1` |
| `BASE_BACKOFF_SECONDS` | `0.5` |

2. Apply `schema.sql`.
3. `uvicorn workflow_engine.api:app` on an uncommon port.

## 7. Workflow registry and handlers

In-process dict, imported by API (for validation) and workers (for execution). Unknown `workflow_name` → `400` on submit. Workers refuse a claimed step whose name is not registered (mark failed; this is a deploy mismatch, not a retryable dependency error).

```text
Workflow(
  name="lab_linear",
  steps=[
    Step("http_post", handler=..., max_attempts=5, timeout_seconds=10),
    Step("pg_effect", handler=..., max_attempts=5, timeout_seconds=5),
    Step("noop",      handler=..., max_attempts=1, timeout_seconds=5),
  ],
)
```

Handler signature:

```text
handler(ctx) -> dict   # JSON-serializable step output
```

`ctx` fields: `job_id`, `step_name`, `seq`, `attempt_count`, `fencing_token`, `worker_id`, `idempotency_key` (see below), `job_input`, `upstream_outputs` (name → output), `should_stop() -> bool`.

**Effect idempotency key** (passed to handlers, sent as HTTP header, used as `lab_effects.effect_key`):

```text
{workflow_name}:{jobs.idempotency_key}:{step_name}
```

Stable across retries and across workers. **Not** including `fencing_token` — that would make every steal a new effect.

### Laboratory handlers (required)

| Name | Behavior | Drill |
| --- | --- | --- |
| `noop` | Return `{}` | Throughput bench |
| `echo` | Return job input | Sanity |
| `http_post` | POST `ctx.job_input["url"]` with header `Idempotency-Key: ctx.idempotency_key` | Duplicate HTTP |
| `pg_effect_naive` | `UPDATE lab_effects SET write_count = write_count + 1` (insert if missing) **always** | Shows duplicate effects after crash |
| `pg_effect_idempotent` | `INSERT … ON CONFLICT (effect_key) DO NOTHING` | Shows effectively-once effects |
| `fail_until` | Fail while `attempt_count < job_input["fail_until"]` | Retry / poison |
| `always_fail` | Always raise | Dead-letter; herd |
| `hang` | Sleep `job_input["seconds"]` while ignoring `should_stop` until process kill | Zombie / timeout |
| `crash_after_effect` | Idempotent write, then `os._exit(1)` | Drill 1 |

Timeout: if the handler thread is still alive after `timeout_seconds`, record attempt `timeout`, take the failure path, **stop heartbeating**. Do not `kill` the thread (Python cannot).

## 8. HTTP API sketch

No auth in V1.

| Method | Path | Notes |
| --- | --- | --- |
| `POST` | `/jobs` | Body: `{workflow_name, idempotency_key, input}`. `201` / `200` as in §5.1 |
| `GET` | `/jobs/{id}` | Job + all steps + attempts. This **is** the state machine dump |
| `GET` | `/jobs?status=&stuck=true` | `stuck`: `running` and `leased_until < now()`, or `pending` and `run_after <= now() - interval '30 seconds'` |
| `POST` | `/jobs/{id}/cancel` | `409` if terminal |
| `POST` | `/jobs/{id}/steps/{name}/replay` | Only if that step is `dead_lettered`; sets `pending`, `run_after=now()`, job `running` |
| `GET` | `/metrics` | Prometheus text |
| `GET` | `/health` | `SELECT 1` |

CLI is a thin client of this API (`submit`, `get`, `stuck`, `cancel`, `replay`). No second write path.

Errors: JSON `{code, message}`. Stable codes: `unknown_workflow`, `conflict_terminal`, `not_dead_lettered`, `not_found`.

## 10. Failure drills → scripts

Each drill is a pytest file that **starts the real worker module** against a throwaway database (testcontainers or Compose). No mocked claim SQL — that would test the mock.

| # | Drill | Script (to implement later) | Invariant |
| --- | --- | --- | --- |
| 1 | Crash after effect, before complete | `drills/test_crash_after_effect.py` | Job not lost. New attempt ≥ 2. Naive `write_count ≥ 2`. Idempotent `write_count == 1`. |
| 2 | Zombie overlap: `hang` longer than TTL, second worker claims | `drills/test_zombie_fence.py` | Two `attempts` rows. Exactly one `succeeded` complete. Late complete → `rejected_fence`. `workflow_fencing_reject_total ≥ 1`. |
| 3 | Poison `always_fail` | `drills/test_poison.py` | Step `dead_lettered` after `max_attempts`. A concurrent `noop` job still succeeds. Runnable healthy depth does not grow without bound. |
| 4 | Retry herd: 1000 `always_fail` with `max_attempts > 1` | `drills/test_retry_jitter.py` | Histogram of `run_after - failed_at` is spread; a no-jitter control (if we temporarily disable jitter in the test) is spiky. Jitter is on by default. |
| 5 | Postgres bounce | `drills/test_postgres_down.py` | Workers log errors, no job marked `succeeded` without a handler run. After DB returns, queued work completes. |
| 6 | Cancel during `hang` | `drills/test_cancel.py` | Job `cancelled`. No later attempt `started`. Step not `succeeded`. |
| 7 | Concurrent duplicate submit | `drills/test_idempotent_submit.py` | 50 parallel `POST /jobs` → 1 job row, 1 set of steps. |
| 8 | Python clock skew | `drills/test_db_clock.py` | Frozen/`datetime` patched worker still stores `leased_until` from `now()`. Claim still uses `now()`. |

Harness helpers (later, still not now): `submit()`, `wait_for_status()`, `kill_worker_pid()`, `count_effects(key)`.

Record in `projects/workflow-engine/BENCHMARKS.md`. Machine shape, worker count, concurrency, handler, Postgres settings.

| Bench | Method | V2 trigger |
| --- | --- | --- |
| Throughput | `noop` jobs/sec vs worker processes × concurrency | CPU idle and skip-locked saturates |
| Schedule latency | submit → first attempt `started_at`, p50/p99 | p99 ≫ poll interval |
| Recovery | `kill -9` → steal visible in `attempts` | recovery ≫ lease TTL |
| Contention | many workers, one runnable step | lock wait / wasted claims |
| Durability | crash mid-submit transaction | lost jobs = 0 |

| Payload | 1KB vs 100KB `input` | claim path bloated |

## 12. Interview map (teach from this design)

| Question | Answer in this V1 |
| --- | --- |
| Exactly-once? | No. At-least-once attempts. Fenced **commits**. Idempotent **effects** if the handler uses the key. |
| Lock vs lease? | Lock leaks on `kill -9`. Lease expires via `now()`. |
| Two workers in one step? | Allowed on steal. Fencing token rejects the stale complete. Side effects may have already happened. |
| Why not Kafka? | We need claim + state in one transaction. A broker gives you a log, then you dual-write. |
| Why not Celery? | Celery retries the task, not a durable per-step state machine you can `SELECT`. |
| Why not Temporal? | Temporal replays history through deterministic workflow code. We store current rows. Cheaper to explain; weaker at long timers/signals. Revisit if drills need that. |
| `SKIP LOCKED` fairness? | None. Starvation is possible under load. Not V1. |
| Sagas / 2PC? | No compensations in V1. No 2PC against HTTP. |
| GIL? | Processes for parallelism and crash isolation; threads for I/O overlap. |
